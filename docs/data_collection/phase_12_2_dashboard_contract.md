New pilot or participant collection is not authorised by this contract. Only synthetic inputs or approved non-research hardware and footage are used for development and acceptance. The Phase 11 external test and retained participant dataset must not be reopened for dashboard development.

## Frozen input boundary
Summaries from the Phase 12.1 schema-valid prediction callback, the active ESP-A1/ESP-A2 numerical health monitor, Camera A statistics and the verified `batamfast-v2` mask state are consumed by the dashboard. The frozen model, preprocessing, confidence, prediction availability and degraded-mode decisions must not be changed by it.
The dashboard state is represented using version 1 of `schemas/dashboard_state.schema.json`. Only the latest summary for each camera-local track, Camera A health, ESP-A1/A2 health, privacy readiness and fixed warning codes are exposed. The inference `session_id` is excluded even though that field is still permitted in the local prediction record.

## Local server and refresh
The Dash server is bound only to `127.0.0.1:8050` and run without debug mode; the displayed snapshot is refreshed once per second. External-network binding is prohibited by this contract. Firebase is neither required nor permitted as a dashboard output in Phase 12.2.
Dashboard snapshots and predictions are presented as the latest state in memory. A second prediction log must not be created and dashboard snapshots must not be persisted by the dashboard. The explicitly configured local prediction JSONL output is still owned by Phase 12.1.

## Health and stale-state policy
- A prediction is marked stale after 5 seconds and must not be presented as current
- Camera A is marked stale after 2 seconds without a new processed frame
- The existing 5-second stale threshold is used for ESP-A1 and ESP-A2
- Packet loss is calculated as a cumulative runtime estimate derived from sequence gaps. A warning is shown only after at least 50 received packets and loss greater than 2%
- Latest prediction is kept separately for each `local_track_id`; cross-track aggregation is prohibited
- Stale predictions may remain visibly labelled for manual diagnosis but may never be reused or styled as current activity
Overall status is `blocked` when the approved privacy mask is unverified, regardless of component health. It is `degraded` when a required component or prediction is unavailable or stale. It is `ready` only when the mask is verified and required components are fresh. Privacy failure therefore takes precedence over operational health.

## Presentation policy
Camera-local track ID, activity, unchanged model confidence, unavailable reason, modality availability, Camera A capture/processing FPS, mask status, ESP freshness, packet loss and fixed warning codes are shown in the interface.
Confidence is labelled **model confidence** and displayed without transformation; no rejection threshold is created. Calibrated certainty must not be implied and a Phase 12.1 prediction must not be changed based on UI logic.
Session IDs, participant identifiers, participant names and role attribution are not shown in the interface. No video component or video route is included. A masked video display for operational use may be reconsidered only through a separately versioned contract and privacy acceptance; it is not included in version 1.
A fixed local code dictionary is used for warnings rather than arbitrary producer-supplied text. Packet payloads, exception strings and identifiers are thereby prevented from being used as a display or retention channel.

## Implementation and acceptance gate
Implementation may be started only against this contract. Every emitted snapshot must be validated by the state aggregator before it is consumed by the Dash layer. Schema-valid state must be rendered by the UI without access to raw features, media or participant records being required.
The state boundary is now implemented in `src/aria/dashboard/state.py`. The frozen contract and every pinned input hash are verified, Phase 12.1 prediction callbacks are validated, only the latest window per local track is retained, and prior tracks are cleared as soon as a newer unavailable window is received. Session and model metadata are stripped before dashboard summaries are produced, stale state is calculated at snapshot time, and every returned snapshot is validated against dashboard-state schema v1.
Independent cumulative in-memory packet, gap and estimated-loss counters are maintained for ESP-A1 and ESP-A2 by the Phase 12.2 aggregator alongside the unchanged historical `NodeMonitor`. Dashboard packet-loss percentages are derived from those new counters and the frozen minimum-sample rule without the hash-listed collection-era monitor being changed. Camera and mask updates are kept explicit; the dashboard is blocked by an unverified mask even if every component is otherwise fresh. Producer text is replaced with fixed warning codes, and no dashboard snapshot or media is persisted.
The validated state is now rendered as a single responsive local page by `src/aria/dashboard/app.py`. Camera-local activity and unchanged three-decimal model confidence, explicit stale or unavailable state, modality availability, Camera A capture/processing rates, verified-mask readiness, ESP-A1/A2 freshness and cumulative packet-loss health, and the frozen warning code with its fixed local message are shown. No image or video component is included, no media route is registered, and fixed text is shown as a fail-closed response if snapshot validation is failed.
The frozen host, port and debug values are read from the verified contract by `scripts/run_local_dashboard.py`, so the network binding cannot be widened by a command-line option. `--demo` and an explicit `synthetic` or `non_research` input-scope declaration are required for the optional preview path, and only non-identifying in-memory state is seeded. Participant and pilot input are not authorised, and no dashboard log is created.
The producer boundary is now provided by `src/aria/dashboard/integration.py`. Metadata-only Camera A records are validated against the existing camera record schema, only Camera A in Zone A is accepted, ESP receive envelopes are validated through the existing active-node schema path, and only health summaries are forwarded to the dashboard aggregator. Completed windows are processed through the unchanged Phase 12.1 service, and the dashboard's latest per-track state is replaced through its existing `on_prediction` callback. Raw camera records, skeletal keypoints, numerical sensor features, source addresses and session IDs are not retained in dashboard state.
That integration path is now exercised by the synthetic preview with the real frozen model rather than a fabricated prediction being injected directly. Camera A health is cleared after camera loss, and the earlier current activity is replaced by a newer unavailable inference window. An otherwise ready integrated state is still blocked by an explicit unverified-mask transition, with privacy precedence retained. The integration is kept in memory, and dashboard persistence, Firebase output and media handling are not added.
Normal single- and multiple-track states, every frozen degraded-modality state, stale predictions and sensors, packet-loss warnings, an unverified mask, model error and identical prediction retries must be covered by acceptance. Localhost-only binding, absence of video components/routes, schema validity and privacy-safe fixed fields must be confirmed. Only synthetic or non-identifying data may be used in screenshots.
